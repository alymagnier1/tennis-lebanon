## Push is dead, and one number explains the whole chain

```
device_push_tokens:  0 rows, 0 users, ever
notifications:       107 rows, 0 delivered, 105 unread
```

**No device has ever registered a push token.** So `process-notifications` has no recipient, nothing is stamped `sent_at`, and the bell badge climbs with no way down.

The cron is a red herring — `tennis_process_notifications` shows 576 successful runs in two days, but that success is the queued HTTP call, not the function's result. Do not read it as "push works".

`5fc5f0c` added registration diagnostics that will say _why_ on the next build.

### `b7c575c` removed the dead end, not the cause

`mark_all_notifications_read` (083) marked delivered rows only, while the centre lists and the bell counts by `scheduled_at`. With 0 delivered, "Mark all read" silently returned 0 forever. Tapping a single notification always worked — `mark_notification_read` never had that guard, contrary to 083's comment.

`106_mark_all_read_matches_the_list.sql` marks everything **due and unread**. Checked against staging before writing: old predicate 0 rows, new predicate 105. Keeps the `scheduled_at` filter so a reminder set for tomorrow is not cleared before it arrives. Marking read does not suppress delivery — `claim_due_notifications` never reads `read_at`.

## Three fixes found by driving the app, not by reading it

1. **`95cf9fe` — the auth back button did nothing.** `sign-in`, `sign-up` and `forgot-password` called `router.back()` directly, which pops nothing when the screen is first rendered: `PublicLayout` redirects rather than pushes, and an emailed link cold-starts onto a route with no history. Surfaced on device as `GO_BACK was not handled by any navigator`; in production it is silent. Now uses `exitAuthScreen`, matching `exitMatchHub` / `exitProfileScreen` / `exitPlayerProfile` / `exitClubDetail`.

2. **`c47b239` — the app promised a code the server had not sent.** `resetPasswordForEmail` returns 200 and sends nothing for an unregistered address (the 09-13 enumeration decision). The screen asserted "We sent a code to X" regardless. Confirmed by requesting a reset for an address that did not exist yet: code screen shown, no `user_recovery_requested` in the audit log. Recovery copy now hedges; sign-up confirmation keeps the definite wording because `signUp` provably created the account.

3. **`9c948d1` (09-13) — `Screen`'s back button sat inside the status bar.** Measured `[63,21][158,116]` against a 132px status bar. `FormUi.Screen` never applied `insets.top`; tab roots hid it by insetting their own header shells.

## Corrections to earlier handovers

**`auth.users.recovery_sent_at` is a dead column on this project.** It still reads 2026-09-11 while the audit log records recovery requests today. It is not evidence of anything. Use `auth_audit_logs` (`source = 'auth_audit_logs'` in the logs stream) — `auth.audit_log_entries` in Postgres is empty here, which is also misleading.

Two "the reset never sent an email" claims were made today off that column and were wrong. The one genuine case was an address with no account.

## `1e0bd3d` — expo-updates, finally

`eas.json` has declared `channel: "staging"` since the profiles were written, but without the package that channel was inert: every JS-only fix cost a full build **and** a reinstall on every tester's phone.

`runtimeVersion` uses the **fingerprint** policy, not `appVersion` — `version` is `0.0.0` with `appVersionSource: remote`, so appVersion carries no signal, and fingerprint refuses to serve an update to a binary whose native code cannot run it. On a pilot a bad OTA reaches everyone at once.

Native module: takes effect from the next EAS build only.
