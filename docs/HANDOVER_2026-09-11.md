## Google sign-in shipped and works

`cfd0485` added it as a second option beside the magic link, never a replacement. Six successful logins on 2026-09-11 with `login_method: oidc`.

**Native flow, deliberately.** `supabase.auth.signInWithIdToken` with `@react-native-google-signin/google-signin`, not `signInWithOAuth`. The OAuth flow returns through `tennislebanon://auth/callback` — the deep-link path that took three wrong diagnoses to fix. The native flow gets an ID token in-process and touches none of it.

`google-sign-in.ts` holds the orchestration and error mapping and is unit tested. `google-native.ts` is the only file importing the SDK, so the logic stays runnable under vitest's node environment.

## Metro and `EXPO_PUBLIC_*`: three distinct traps, one week

Worth reading as a group, because each looks like the others and none is obvious.

1. **Dynamic keys are not inlined.** Metro replaces `process.env.EXPO_PUBLIC_FOO` only on a **static property read**. Passing bare `process.env` into `loadClientEnv`, which indexes dynamically, left every value `undefined` in release builds. Fixed in `c55eee6`; `apps/mobile/src/lib/env.ts` must keep listing each key literally.
2. **A build profile's `env` overrides the EAS environment.** `eas.json`'s `staging.env` beats a value set in the Expo dashboard, silently. Anything set in both places is governed by `eas.json`.
3. **`.env` is read from the app directory, not the repo root.** Expo loads `.env` from the project containing `app.json` — `apps/mobile/` — so the monorepo-root `.env` is invisible to Metro started there. `apps/mobile/.env` now exists (gitignored) holding only the `EXPO_PUBLIC_*` values; the service-role key is deliberately left out of the mobile tree.

The symptom of #3 is spectacular and misleading: every route reports _"missing the required default export"_ plus a `Cannot read property 'ErrorBoundary' of undefined`. That is one cause — `env.ts` throws at import, so no module finishes evaluating.

`EXPO_PUBLIC_*` values are inlined at transform time, so after changing `.env` restart Metro with `--clear`. A reload alone can serve a cached bundle with the old values baked in.

## Local development

**Use an EAS development build, not `expo run:android`.**

Local Gradle is a dead end on this machine: the prebuild template pulls Gradle 9.3.1, which removed `JvmVendorSpec.IBM_SEMERU`, and a plugin resolved from Gradle's own Maven cache still references it. Nothing in `node_modules` does, so it is not something the project can fix.

```bash
cd apps/mobile        # expo is a dependency here, not at the repo root
npx expo start --dev-client --clear
```

`a3b660f` added `expo-dev-client`, which `eas build --profile development` refuses to run without. Install the dev-client APK once, and every JS change reloads in seconds afterwards — the client id comes from `apps/mobile/.env` via Metro, so even that needs no rebuild.

Running any `expo` command from the repo root fails with _"the module `expo` is not installed"_ — it is a dependency of `apps/mobile`.

## Next, in order

### 1. The https invite page — the acquisition loop is still inert

Unchanged from yesterday and now the most valuable open item.

[`invite-link.ts`](../apps/mobile/src/lib/invite-link.ts) builds `tennislebanon:///invite/${token}` — a **custom scheme**. `app.json` has no `intentFilters`, no `associatedDomains`, and the dashboard has no `/invite` route. A WhatsApp invite therefore reaches a non-user as a dead string. **The loop only closes for people who already have the app**, which makes it a coordination feature rather than an acquisition channel.
