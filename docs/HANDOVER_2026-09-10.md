## What was wrong, and what fixed it

### The staging APK would not open

Three independent faults, all fixed in `c55eee6`. Any one alone still crashes.

| Fault                                                                                | Why                                                                                                                                                               |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eas.json` staging profile supplied no `SUPABASE_URL` / `ANON_KEY` / `SUPPORT_EMAIL` | `packages/config/src/env.ts` requires all three and rejects a `.invalid` support address outside `local`. It throws at import, before React mounts                |
| `env.ts` passed bare `process.env` into `loadClientEnv`                              | Metro inlines `EXPO_PUBLIC_*` only on a **static property read**. `loadClientEnv` indexes with dynamic keys, so every value stayed `undefined` in a release build |
| Expo SDK 56 package versions misaligned                                              | `expo-font ^57.0.1` and `expo-image-manipulator ~14.0.8` predate SDK 56's unified `56.x` versioning                                                               |

The staging env vars now exist in **two** places: `eas.json`'s `env` block and the EAS "preview" environment. The build profile wins. Rotating the anon key in the EAS dashboard alone would silently do nothing.

### Sign-in showed "invalid or expired" on a login that had succeeded

Worth understanding, because three plausible explanations were wrong before the right one.

Staging auth logs showed `/verify` → `303` → **Login** on every recent attempt, with `auth.sessions` gaining rows — while the founder saw an error. So the server was minting sessions and the app was rejecting the callback.

`fc0583b` added a **redacted diagnostic** to the callback error screen: scheme, host, path and parameter _names_ only, never a value — the callback carries access and refresh tokens, and a test asserts a token cannot reach that string. It renders whenever `APP_ENV !== "production"`.

It reported `no url delivered`, which settled it: **a subscription race.** A deep link that resumes an already-running app fires its `url` event while expo-router is still routing — before the destination screen mounts. `Linking.useURL()` subscribes from inside that screen's effect, so it is installed after the event and never hears it. `getInitialURL()` returns null alongside it, because the link did not _launch_ the app.

`9530cb0` fixes it with three sources, in order:

1. `authUrlFromParams` — rebuilds the callback from expo-router's route params, the only place the query survives if the router consumed the link
2. `installDeepLinkCapture` — subscribes from the **root layout at module scope**, the earliest point the app can listen, and buffers the newest link
3. `getInitialURL()` — cold start

`waitForAuthCallbackUrl` now re-reads the buffer on every attempt. The previous eight-attempt poll could never have worked: `liveUrl` is a closed-over constant, so it re-read the same `null` eight times.

The diagnostic now names which sources held a URL (`live=n captured=y params=n`), so a future failure says _where_ the link was lost.

**This is committed but not yet verified on a device.** No build has been made since `9530cb0`.

### A separate, real "invalid or expired"

Distinct from the above and still true: requesting a second sign-in email invalidates the first, and Supabase returns `error_code=otp_expired`. `parseAuthUrl` now carries that code, `completeAuthFromUrl` returns a typed reason, and the callback screen renders `auth.callbackExpired` ("only the newest email works") instead of the generic error. `auth.checkEmailHint` no longer invites a resend without warning that it kills the previous link.

## Next, in order

### 1. Rebuild and confirm sign-in

```bash
eas build --profile staging --platform android
```

Uninstall the old APK first. Then tap a sign-in link. Success is landing inside the app. Failure now prints the source line under the error — report it verbatim, it is diagnostic.

Highest value, because it unblocks judgement on everything else.

### 2. The https invite page — the acquisition loop is currently inert

[`invite-link.ts`](../apps/mobile/src/lib/invite-link.ts) builds `tennislebanon:///invite/${token}` — a **custom scheme**. `app.json` has no `intentFilters` and no `associatedDomains`, and the dashboard has no `/invite` route.

So a WhatsApp invite reaches someone as a dead string unless they already have the app. **The loop only closes for existing users, which makes it a coordination feature rather than an acquisition channel.**

Two stages:

- **Now:** a public `/invite/[token]` route on the Vercel dashboard at `racketbound.com`, rendering the match and offering _Open in app_ / _Get the app_. Change `buildMatchInviteUrl` to return that https URL. Works in WhatsApp today, no domain verification needed.
- **Later:** verified App Links (`intentFilters` + `assetlinks.json`) and Universal Links (`associatedDomains` + AASA) so it opens the app silently.

### 3. `expo-updates` is not installed

`eas.json`'s staging profile declares `channel: "staging"`, but without `expo-updates` that channel is inert. Every JS-only fix therefore costs a 40-minute rebuild **and** a reinstall on every tester's phone. For a 50-player pilot that is the difference between shipping a copy fix in seconds and in a day.

```bash
npx expo install expo-updates
```

then `eas update:configure`. Founder's call — it changes how the app ships — but worth deciding before cohort A, not after.

### 4. Leftover English in `fr.json`

About twenty French strings are still English, mostly the onboarding notifications screen. [`locales.test.ts`](../packages/i18n/src/locales.test.ts) only enforces that **Arabic** critical-flow copy differs from English; there is no French equivalent, which is why this went unnoticed. Consider adding one, with an allowlist for legitimately-identical keys (Courts, Format, Match, Participants…).
